## Draft Registry reply

Hi Sebastian,

Thanks for the revised Registry schema. I have tested the schema and example. The project identifier, string registry/program identifiers, dated registration records and update timestamp are useful improvements on our earlier feedback.

The standalone example validates. I have a few remaining points:

1. Please make the project join explicitly the persistent global project identifier, with the registry's project identifier separate. I've prepared a worked example that preserves the global ID when the registry/native ID changes.
2. The status array is still separate from the registration records. Could each status event identify its registration and carry a timestamp and sequence? Otherwise a transfer with multiple registrations leaves the status history ambiguous.
3. Please define whether multiple current registrations are valid. The schema currently accepts two, no registrations at all, and an exit date before the registration date. Some checks need a semantic validator rather than JSON Schema, but the intended rules should be explicit.
4. `Woodland Carbon Code` is still absent from the crediting-program name enum, although Peatland Code is present. Supplying the WCC name fails validation.
5. The supplied Full List example fails five subdivision enum checks. Please regenerate it from the v2.1.0 baseline and check that all example fields occur at their schema-defined paths; I also found 25 undeclared paths in that example.

I can walk through these examples at the TWG meeting.

Best,
Mark

## Draft Verification reply

Hi Sebastian,

Thanks for sending both alternatives. My preference is **VAE**, with each verification represented as an independently identifiable event linked to the persistent project ID. That fits repeated monitoring periods, references from issuances and a verification API resource. A project response can still embed those same events. Both layouts should share one event definition and the same identifier rules.

Both standalone examples validate. Keeping each event's details and quantity together resolves the earlier parallel-array concern, and making the digital credential fields optional is helpful.

The remaining points from my checks are:

1. Both schemas reject an in-progress verification without a verification date, verified quantity and report URL. Please require those outcome fields conditionally when the event is completed, so pending audits do not need invented results.
2. Both accept a negative verified quantity and a non-URL report link. Please add appropriate numeric constraints and URI formats. They also accept duplicate event IDs; uniqueness needs a semantic check.
3. Status history still needs timestamp, sequence and actor information. I've included an ordered-history proposal in the API demo.
4. Please make `verification_project_id` unambiguously reference the persistent global project identifier. The example's native-looking `VCS-4721` value leaves the join unclear.
5. Please clarify the uncertainty margin's basis (percentage, fraction or absolute quantity) and settle unit codes. `tCO2` is rejected; if `tCO2e` is the intended contract, the earlier examples and guidance should consistently use it.
6. Please regenerate the Full List variants from v2.1.0 and audit example paths. Both currently pass validation despite containing fields outside declared schema paths (25 in VAE and 16 in PAE).

I have WCC, Peatland Code and VCS worked examples ready to discuss on Monday, including project identity, lifecycle, unit states, issuance preconditions and audit history.

Best,
Mark
