# ADR 0006: Kysely, SQL migrations, Postgres first

Status: accepted. Date: 2026-09-20.

## Context

The same database schema must run in three places with no drift: plain Postgres 17 under `docker compose` for forkers, a local Supabase stack under `supabase start`, and the hosted Supabase project under `supabase db push`. The Supabase CLI applies `supabase/migrations/*.sql` files in name order; anything it cannot read is not portable. The API is the only database client, so there is no row-level security, no `auth.jwt()`, and no other Supabase-only feature to lean on. Triggers carry real logic (versioning, parent touch, status coherence, event capture, `NOTIFY`), and a range-exclusion constraint guards unit block overlaps.

## Decision

Migrations are hand-written SQL files in `supabase/migrations/`, named with the Supabase timestamp convention. A small runner (`apps/api/src/db/migrate.ts`) applies them in order inside transactions and records a SHA-256 checksum per file in `cdop.schema_migrations`. It refuses to re-run a modified file. It refuses to run at all when `supabase_migrations.schema_migrations` exists, so the CLI and the runner never both own a database. Queries go through Kysely on `pg`, with types generated by `kysely-codegen` (`pnpm db:types`). The only required extension is `btree_gist`; PostGIS is optional and guarded. Numeric and bigint columns are parsed as JavaScript numbers.

## Consequences

- Every environment runs the same files; there is no ORM-generated migration to reconcile with the CLI.
- Triggers and constraints live where they execute, in SQL, and are readable in one place.
- Types follow the database, not the other way round; after a migration, regenerate.
- Bulk paths (seed, simulator) set session settings to suppress the parent-touch and row-event triggers, and emit their own richer events.
- No Supabase dependency at runtime: `DATABASE_URL` is enough, and Supabase Studio is a convenience for hand edits.

## Alternatives considered

- **Prisma**: its own migration format and schema DSL; harder to share files with the Supabase CLI, and no first-class exclusion constraints.
- **Drizzle**: TypeScript-first schema with generated SQL; workable, but the source of truth would move out of the SQL files the CLI runs.
- **node-pg-migrate or Knex migrations**: JavaScript migrations the CLI cannot read.
- **Raw `pg` without a query builder**: every query becomes untyped string assembly.
